**Why the candidate LOS and Fresnel values differ, and what it means.** Every LOS disagreement is a grazing path: my minimum clearance is within 0.20 m of zero, so the yes/no depends on where the path is sampled. The producer (`relay_tower.link_profiles`) sorts the paths by length, groups them in blocks of 256, and gives every path in a block ceil(longest/5 m) intervals, so sample positions are not at fixed distances. When I re-implement that sampling in my own code (column `blk`), the LOS bits and the Fresnel values come back almost exactly; the few remaining entries are paths whose block membership depends on how equal distances are ordered. So the file is computed as documented, and the differences are sample positions, not terrain or geometry. Finding for the producer: samples about 5 m apart can step over a short terrain feature, so the published minimum clearance (and Fresnel per-cent) can be slightly optimistic. On paths that are open at 1 m steps the published minimum clearance is optimistic by at most the second number in the table above (IM1). The app uses the plain LOS rule (`link_rule: los`), so none of this changes a published link fraction; it only matters if someone applies the 0.6 F1 Fresnel rule to these arrays.

## Scope and limits

- Recomputed: every value the app shows for the relay (direct, best tower per height, networks, timelines) and the per-candidate arrays listed above, plus the derived `height_curve`. Not re-run: the greedy search itself (I checked the towers it chose, not that no other choice is better; the contract calls it a heuristic) and the `link_budget` block, which is a stated assumption set, not a terrain result. No published file has a `coverage` map (`params.coverage_side_km = 0`). Each best-tower entry matches its own candidate-array entry (`candidate_consistency` in the JSON).
- Same terrain chain as the producer (input definition from each file's `dem_sources` / `input_identity`): source gates measured from the lander, PGDA windows = squares of half-width = gate. Terrain was read from the NASA originals, not from the producer's caches.
- LOS sampled every 1 m (production at most 5 m). For the published best towers and network hops the Fresnel differences are small (table above). For the candidate arrays the producer's sample positions matter; see the candidate section.
- Geometry only: no RF budget, no Earth-station scheduling, no tower power model.

Reproduce (order matters; each step resumes per site, `--site ID` limits it):

```
python pipeline/crosscheck_relay_dongju.py fetch             # DEM windows from NASA servers (~3 GB, not committed)
python pipeline/crosscheck_relay_dongju.py run               # lander, best towers, networks, timelines (~4 min)
python pipeline/crosscheck_relay_dongju.py candidates        # 5,025 candidates: ground, slope, LOS, Fresnel (~6 min)
python pipeline/crosscheck_relay_dongju.py candidates-earth  # 5,025 candidates: tower Earth (~6 min per site)
python pipeline/crosscheck_relay_dongju.py report            # writes docs/crosscheck_relay_dongju.{json,md}
```
